# Admin Dutch Localization — Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> to implement this plan task-by-task (native execution — see Execution
> Handoff at the end). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Default the admin UI to Dutch, let each admin switch their own
admin UI to English, with zero leakage onto the English public site or
customer emails.

**Architecture:** A flat `t(key, locale)` dictionary helper (`nl.json`
default, `en.json` complete baseline/fallback) scoped entirely to
`app/admin/**`/`components/admin/**`; a new `AdminLocale` enum on `User`
read into the NextAuth session; a self-scoped `PATCH /api/admin/me/locale`
mutation; a switch control in `AdminTopNav`. No i18n routing framework.

**Tech Stack:** Next.js 16 App Router, Prisma/PostgreSQL, next-auth v5
(JWT), existing `lib/api-auth.ts` auth guards, Vitest.

**Spec:** Phase 1 report below (this same file, retained for reference) +
the user's approved Phase 2 brief (six flagged calls, all approved).

## Global Constraints

- Dutch (`AdminLocale.NL`) is the default; English is opt-in per admin.
- `t()` falls back to `en.json` on a missing key — never a raw key, never blank.
- Public site and customer-facing emails (order confirmations, newsletter)
  stay English, unconditionally — no locale parameter touches them.
- No locale routing, no visitor-facing switcher.
- Every migration: `prisma migrate dev --create-only`, then
  `npx tsx scripts/clean-migration.ts <path>`, then hand-verify the diff
  (`docs/instructions/branching.md`).
- Every new/changed admin API route independently calls `requireAdmin()` or
  `requireAdminUserId()` — page-level `proxy.ts` protection does not cover
  `/api/admin/*` (`docs/instructions/authorization-boundaries.md`).
- Tests are behavioral, never assert CSS. Existing tests asserting English
  display text become Dutch-text assertions where this task intentionally
  changes displayed text — a sanctioned Test Contract exception because the
  interface's observable behavior changed on purpose, not a broken test
  being "fixed." No other existing test gets changed.
- Branch `feature/admin-i18n`, fast-forward merge, delete after.

## Review Focus

- **Mismatched dictionaries.** A key in `nl.json` with no entry in
  `en.json` (or vice versa) breaks the fallback invariant. `t()`'s own type
  signature must make this a compile error, not a runtime gap — covered by
  Task 2.
- **Stale session locale.** The JWT caches `locale`; switching it via the
  PATCH route updates the DB but not the live session token until the
  client forces a refresh. A switch that "succeeds" but doesn't visibly
  change the UI until next login is a real regression — covered by Task 6.
- **Day-name index drift.** `OpeningHoursForm`'s new Dutch day-name lookup
  must stay aligned with `lib/opening-hours.ts`'s `DAY_NAMES` ordering
  (Sun=0…Sat=6) without ever importing or editing `DAY_NAMES` itself — a
  transposition here is invisible on the public site and only shows up as
  wrong day labels in the admin hours editor. Covered when Stage 2 converts
  Opening Hours (§Stage 2, Settings section).
- **Locale-mutation tampering.** `PATCH /api/admin/me/locale` must ignore
  any user id in the request body and act only on the session's own id —
  one admin must not be able to flip another admin's locale by passing
  their id. Covered by Task 5.
- **Enum drift.** `enum-labels.ts`'s maps must cover every member of all
  five enums at compile time, so a future new enum value (e.g. a third
  `Condition`) fails the build instead of silently rendering blank — covered
  by Task 3 (exhaustive `Record<EnumType, string>`, not an optional map).

  ```ts
    if (user) {

    return session;
  },
  ```

  ```ts
  export async function PATCH(req: Request) {
    const userIdOrResponse = await requireAdminUserId();
    if (userIdOrResponse instanceof Response) return userIdOrResponse;
    const parsed = parseLocaleChange(await req.json());
    if (!parsed.ok) return Response.json({ error: parsed.error }, { status: 400 });
    await db.user.update({ where: { id: userIdOrResponse }, data: { locale: parsed.data.locale } });
    return Response.json({ ok: true });
  }
  ```

## Appendix: Phase 1 Report (reference)

## Context

The admin back-end must default to Dutch. Each admin can switch their own
admin UI to English. The public site and customer emails stay English. No
locale routing. No visitor-facing switcher.

Three Explore agents mapped: (1) every admin route/component and its
user-facing strings, (2) the admin/public shared-component boundary, (3) the
auth/session plumbing and any existing i18n code. Findings below.

## 1. Admin string surface — confirmed scope

Admin UI lives under `app/admin/**` (pages/layouts) and `components/admin/**`
(forms/editors), plus two shared chrome files: `components/layout/AdminTopNav.tsx`
and `components/layout/AdminSubNav.tsx`.

Sections and their string load: Login, Catalog (products, suppliers,
orders overview, labels/genres/artists/product-types via shared
`ReferenceSection`), Content (blog posts, newsletter composer), Customer
Orders, Settings (opening hours, notices, subscribers, users).

String categories present in every section: nav labels, page titles, table
headers, button text, field labels/placeholders, validation/toast messages,
empty states, and raw enum values with no friendly label.

One dead route: `app/admin/posts/page.tsx` (a `Placeholder` stub, not linked
from any nav — the real blog-posts admin is `app/admin/content/posts`).
**Recommendation: leave it out of scope.** It is unreachable by any admin, so
translating it buys nothing. Flagging it per house rule (mention dead code,
don't touch it unasked) rather than deleting or translating it.

## 2. Shared admin/public boundary — the critical finding

Two Explore passes, independently grep-verified, confirm exactly one
real risk and one component that's safe by construction:

- **`lib/opening-hours.ts`'s `DAY_NAMES`** (English weekday array) is
  imported by BOTH `components/admin/OpeningHoursForm.tsx` and the public
  `app/(public)/visit/page.tsx`. Translating it in place would put Dutch day
  names on the public Visit page. **Plan: never edit `DAY_NAMES`.** Add a
  separate admin-only Dutch day-name lookup that `OpeningHoursForm` uses
  instead of importing `DAY_NAMES` directly.
- **`components/PostBody.tsx`** is the only JSX component rendered on both
  sides (admin's `CustomerOrdersEditor` and the public blog post page). It
  owns zero strings of its own — it only renders whatever markdown string
  its caller passes in. It is safe as-is. **Plan: add no text or props to
  `PostBody` itself** — any new admin-only chrome (e.g. a "Preview" label)
  stays in `CustomerOrdersEditor.tsx`.
- Everything else that looked shared by name — `ProductRow`, `Combobox`/
  `MultiCombobox`, `NewsletterForm`, `SocialLinks`, `SiteHeader`/`SiteFooter`/
  `NoticeBanner`, `lib/catalog.ts`'s `joinArtistNames`/`joinGenreNames`/
  `isRestock`, `lib/api-client.ts`/`lib/use-async-action.ts`'s shared error
  strings — is confirmed single-sided (grep-verified both ways, including a
  direct re-check I ran: zero `app/(public)` hits for `api-client`/
  `use-async-action`/`apiSend`/`useAsyncAction`). Free to localize without
  cross-boundary risk.
- `lib/relative-date.ts`, `lib/datetime.ts`, `lib/dymo-label.ts`,
  `lib/markdown.ts`, `lib/stock.ts` are all admin-only. `lib/dymo-label.ts`
  already hardcodes one Dutch literal (`"Tweedehands"`) for the physical
  label printout — unrelated to this task, confirms Dutch strings already
  coexist safely in admin-only `lib/` code.

## 3. Enum labels — a gap this task must close, in one place

Five enums render in the admin with no consistent friendly-label layer today:

| Enum | Values | Current state |
|---|---|---|
| `Condition` | NEW, SECONDHAND | rendered raw, no mapping anywhere |
| `PostStatus` | DRAFT, PUBLISHED | rendered raw, no mapping anywhere |
| `StockTransactionType` | IN, OUT, ADJUSTMENT | rendered raw, no mapping anywhere |
| `SupplyOrderStatus` | PENDING, PARTIAL, RECEIVED | ad-hoc English-only mapping, inline in `OrderLineRow.tsx` |
| `SubscriberStatus` | PENDING, CONFIRMED | ad-hoc English-only mapping, inline in the subscribers page |

Localizing these means writing a Dutch label for every value regardless.
**Plan: consolidate all five into one new `lib/i18n/enum-labels.ts`**
(bilingual maps, keyed by locale), and replace the two existing inline
mapping functions with it. This isn't speculative abstraction — it's work
the task requires anyway, done once instead of scattered and duplicated
across old and new call sites. Flagging it because it touches existing
working code (`OrderLineRow.tsx`, the subscribers page) beyond pure addition.

## 4. Proposed approach

- **`lib/i18n/`**: `t.ts` (helper), `nl.json`, `en.json`, `enum-labels.ts`
  (§3). Plain modules, same pattern already proven admin-safe by
  `lib/relative-date.ts` etc. — nothing public ever imports from here, so
  no routing framework or build-time scoping is needed.
- **Fallback order:** look up the active locale's dictionary; if the key is
  missing, fall back to `en.json`; never return the raw key or blank. (`en.json`
  is written first/is the complete baseline when new admin UI ships; `nl.json`
  translation can lag by one commit without ever showing broken text.)
- **Dates/numbers:** `Intl` formatters tagged `nl-NL` or `en-US` by the
  active admin's locale. Two existing admin-only formatters —
  `lib/catalog.ts`'s `shopDisplayDate`/`shopDisplayTime` (hardcoded
  `en-US`) and `lib/relative-date.ts`'s `fullDate` (hardcoded `en-GB`) — get
  their locale tag switched to follow the admin's preference. Their fixed
  `Europe/Amsterdam`/`SHOP_TZ` timezone does not change — timezone and
  locale are orthogonal, only the locale tag moves.
- **`lib/relative-date.ts`'s hand-rolled relative-time strings** ("3 days
  ago", "just now") get Dutch equivalents through the same `t()` dictionary,
  since this file is confirmed admin-only.
- **Language switch control:** in `AdminTopNav.tsx`, next to "Sign out" —
  always visible, one click, no detour through Settings. One location only.
- **Login page** (`app/admin/login/page.tsx`): renders before any session
  exists, so no DB preference is available yet. **Interpretation:** hardcode
  it to Dutch, no switcher — consistent with Dutch being the system default.

## 5. Schema + API plan

- **Schema:** add `enum AdminLocale { NL EN }` and `locale AdminLocale
  @default(NL)` to `User`. An enum, not a free string, matches this
  schema's existing convention (`Condition`, `PostStatus`,
  `SupplyOrderStatus`, `StockTransactionType`, `SubscriberStatus` are all
  enums). Flagging as an architectural decision per the project's test/interface
  rules.
- **Migration:** `prisma migrate dev --create-only`, then
  `npx tsx scripts/clean-migration.ts <path>`, then hand-verify the diff —
  per `docs/instructions/branching.md`. A plain `ALTER TABLE "User" ADD
  COLUMN` is not expected to trigger the known search-infra drift, but the
  hand-verify step stays mandatory regardless.
- **Session:** extend `lib/auth.config.ts`'s `jwt`/`session` callbacks to
  carry `locale` (today they carry only `id`).
- **Mutation endpoint:** locale is a **self-only** preference ("each admin
  switches their own"), unlike the existing `PATCH /api/admin/users/[id]`
  (built for one admin editing any account's email/password, by id — both
  admins already have equal access to any id). Reusing that route would let
  admin A silently flip admin B's display language. **Plan: a new
  self-scoped route** (e.g. `PATCH /api/admin/me/locale`) that reads the
  target user id from the session via `requireAdminUserId()`, not from a URL
  param. Validation follows `lib/user-input.ts`'s existing
  `parseEmailChange`/`parsePasswordChange` shape (`{ok:true,data}|{ok:false,error}`).
  Still just `requireAdmin()` — no role check needed, per
  `docs/instructions/authorization-boundaries.md` (no role tiers in this app).
