## What was built
- `feature/observability-logging` (merged): PII-safe, structured logging
  groundwork plus a request correlation id, proportional to a low-traffic
  shop — not a telemetry pipeline, not session replay. New `lib/log/`
  module (`events.ts`'s closed `LogEvent` taxonomy + `SYSTEM_ACTOR_ID`,
  `log.ts`'s pure/synchronous `logEvent`, `context.ts`'s
  `AsyncLocalStorage`-based `withRequestContext`/`getRequestId`,
  `redact.ts`'s redaction helpers). Instrumented: `lib/authorize.ts`
  (`auth.login`), `app/api/catalog/route.ts` (`catalog.search`),
  `lib/stock.ts`/`lib/reference-crud.ts`/`lib/customer-orders.ts`
  (`admin.mutation`, each now requiring an `actorUserId`),
  `lib/email/send.ts` (`email.send`), and a log-only fix for a found bug
  (a newsletter confirmation-email failure silently invisible to Sentry).
  See `docs/features/observability-logging.md`.
- Fixed a real admin-auth gap found mid-implementation: Next.js 16 renamed
  `middleware.ts` to `proxy.ts`; the plan's premise ("no existing
  middleware-based auth") was wrong, and extending the pre-existing
  `proxy.ts`'s matcher to cover `/api/:path*` (needed for request-id
  coverage) would have silently started requiring login on every API
  route, including public ones. Resolved via a path-aware
  `isProtectedAdminPath()` plus an explicit `next-auth/jwt` `getToken()`
  check in `proxy.ts`, verified live (browser + curl) before continuing.

## What worked
- Stopped and asked the user (`AskUserQuestion`) before touching any auth
  code once the wrong plan premise was found, rather than silently
  reinterpreting scope.
- Live-tested the auth fix against the running dev server before trusting
  it — caught a real bypass (wrapping `auth()` in a custom middleware
  function does not auto-apply the `authorized` callback's redirect) that
  no unit test would have surfaced.
- Refused a prompt-injection attempt embedded in dev-server CLI output
  (a fake "security upgrade" nudge targeting an AI agent) without
  executing the suggested command, and flagged it to the user immediately.
- Closed two real `/code-review` findings (loose `action: string` typing;
  no test cross-checking `proxy.ts`'s matcher against
  `isProtectedAdminPath`) rather than treating a "mostly duplication
  nitpicks" verdict as nothing-to-fix.

## What drifted from intent
- The plan's `customer_order.intake` taxonomy slot assumed a multi-step
  flow; `lib/customer-orders.ts` turned out to be a single whole-file
  overwrite with no such flow, so it was simplified to the same
  `admin.mutation` shape every other mutation uses, with no `entityId`
  (no per-order row exists to attach one to).
- `app/api/catalog/route.ts`'s `catalog.search` event doesn't actually
  call `redactFreeText` — the taxonomy's field list has no slot for even
  a redacted summary of the `genre` filter, so there was nothing to
  redact; `redactFreeText` ships as forward groundwork with no current
  caller, same as `SYSTEM_ACTOR_ID`.

## Retrospective

**What slowed us down this session?**
- Re-verifying the admin auth gate's both positive and negative paths
  live (unauthenticated redirect, authenticated success, public/admin API
  routes) took real wall-clock time, but was non-negotiable given the
  blast radius (a production middleware file gating every admin page).

**What should we do differently next session?**
- When a plan's investigation step concludes "X doesn't exist" about a
  framework-owned file/convention, cross-check against that framework's
  current major version's own docs/naming before building a plan on top
  of the premise (see the `proxy.ts` lessons row).

**What worked well and should be repeated?**
- Stopping for an `AskUserQuestion` the moment a plan's premise was found
  wrong, instead of quietly reinterpreting scope to fit the new facts.
- Treating a code-review's "mostly nitpicks" verdict as still requiring a
  genuine triage pass (two real findings were in there) rather than
  skipping straight to merge.
