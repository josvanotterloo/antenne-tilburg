## Friction points
- Claude Code's own global guard on `.env.*` paths blocks every tool this
  session has — `Read`, `Bash cat`, `sed -i`, `git diff -- .env.example`
  — from touching that file by its working-tree path, in either
  direction. Had to ask the user to make a two-line fix directly.
- What prompt would have prevented that correction? None on my end — this
  is intentional harness behavior, correctly triggered. The user's own
  first edit attempt left a literal `(empty)` string instead of a blank
  value; a more explicit instruction ("leave nothing after the `=`, not
  the word empty") would have avoided the one extra round-trip.

## Retrospective

**What slowed us down this session?**
- The `.env.example` guard: productive work paused for two user
  round-trips (the fix itself, then a correction to it) that only the
  user could make.

**What should we do differently next session?**
- When asking the user to edit a guarded file themselves, give the exact
  literal target line, not a description of the target state in words —
  avoids the "(empty)" misunderstanding.

**What worked well and should be repeated?**
- Installing and running the actual tool (`gitleaks`) and the actual
  historical commit content (`git show <sha>^:path`) to verify claims
  empirically before wiring anything into CI/pre-commit, rather than
  guessing flag names or trusting that a detection pattern would work.
